--- title: Instalação group: Começando desc: Requisitos, como compilar e executar o jar, instalar como serviço systemd e expor a interface com HTTPS. ---

Requisitos

  • Java 21: JDK para compilar, JRE para executar.
  • Maven 3.9 ou superior, só para compilar.
  • O utilitário ping no PATH. As checagens ICMP chamam o ping do sistema operacional.
  • Linux, macOS ou Windows. O ICMP só foi validado em Linux.
  • Um navegador moderno. Nenhum plugin nem acesso à Internet é necessário: todas as bibliotecas da interface vêm no próprio jar.

Compilar e executar

git clone <url-do-repositório> omnidude
cd omnidude
mvn clean package
java -jar target/omnidude-0.1.0-SNAPSHOT.jar

Abra http://127.0.0.1:8080. O banco e a chave de criptografia são criados na pasta ./data (mude com OMNIDUDE_DATA_DIR).

Primeiro acesso

O usuário inicial é admin. Há dois modos de saber a senha:

  • Gerada: uma senha aleatória aparece uma única vez no log de inicialização, num bloco “Primeiro acesso”. O sistema exige trocá-la no primeiro login.
  • Definida por você: inicie com OMNIDUDE_ADMIN_PASSWORD. Útil em laboratório e automação; neste caso a troca não é exigida.
OMNIDUDE_ADMIN_PASSWORD='uma-senha-forte' java -jar target/omnidude-0.1.0-SNAPSHOT.jar

A variável só vale na criação do usuário (banco vazio). Depois disso, a senha é trocada pela interface ou por Configurações → Usuários.

A lista completa, com as variáveis de proxy e as propriedades omnidude.*, está em Referência.

Guarde a chave. As credenciais SNMP e dos canais de notificação ficam cifradas no banco com a chave de secret.key (ou OMNIDUDE_SECRET_KEY). O backup do banco não inclui a chave: sem ela, esses segredos ficam ilegíveis.

Instalar como serviço (systemd)

Em um servidor Linux, use a unidade pronta da pasta packaging/. Ela roda o OmniDude como o usuário sem privilégios omnidude, com o sistema de arquivos somente leitura (exceto /var/lib/omnidude) e só a capacidade CAP_NET_RAW, usada pelo ping. A análise systemd-analyze security dá exposição 1,7 (OK).

  1. Instale o Java 21 e o ping. 
    sudo apt install openjdk-21-jre-headless iputils-ping
  2. Compile o jar (mvn clean package).
  3. Rode o instalador como root. Ele é idempotente: pode ser repetido. 
    sudo ./packaging/install.sh --start
  4. Acompanhe o log. Se você não definiu a senha, ela aparece aqui. 
    journalctl -u omnidude -f
CaminhoConteúdoDono / modo
/opt/omnidude/omnidude.jaraplicaçãoroot, 644
/etc/omnidude/omnidude.envconfiguração e segredos (OMNIDUDE_*, JAVA_OPTS)root, 600
/var/lib/omnidude/banco, secret.key, backupsomnidude, 700
logsjournal do systemdjournalctl -u omnidude

Atualizar e remover

# atualizar: compile o jar novo e rode o instalador de novo
mvn clean package && sudo ./packaging/install.sh

# remover o serviço, mantendo dados e configuração
sudo ./packaging/uninstall.sh

# remover TUDO (inclui banco e chave; espera 5 s)
sudo ./packaging/uninstall.sh --purge

As migrações do banco rodam sozinhas na partida; configuração e dados não são tocados na atualização.

Ping sob o isolamento. A unidade concede CAP_NET_RAW ao serviço. Se o ping ainda falhar, libere o ICMP sem raw socket: echo 'net.ipv4.ping_group_range = 0 2147483647' | sudo tee /etc/sysctl.d/90-ping.conf && sudo sysctl --system. Para testar como o serviço enxerga: sudo -u omnidude ping -c1 192.168.0.1.

A unidade e os scripts foram validados com systemd-analyze verify e por testes automatizados, mas a instalação como root em um servidor real ainda não foi exercitada. Faça um teste de fumaça: systemctl status omnidude, abra a interface, crie um dispositivo e confira o ping.

Acessar de outras máquinas

Por padrão o OmniDude escuta só em 127.0.0.1: só a própria máquina o alcança. Para abri-lo pelo IP da máquina (por exemplo http://192.168.1.10:8080), há três caminhos, do mais simples ao mais indicado:

OpçãoComoIndicada quando
A. Escutar na rede (HTTP)só OMNIDUDE_BINDRede interna confiável, laboratório, primeiro teste.
B. TLS no próprio OmniDudeOMNIDUDE_BIND + certificado (SERVER_SSL_*)Você quer HTTPS sem instalar outro programa.
C. Proxy reverso com HTTPSnginx, Caddy ou Apache na frenteAcesso de várias pessoas, certificado de verdade, exposição além da rede interna. Recomendada.

Opção A: escutar na rede (HTTP)

Mude o endereço de escuta com OMNIDUDE_BIND:

ValorEfeito
127.0.0.1 (padrão)Só a própria máquina.
0.0.0.0Todas as interfaces IPv4 da máquina: qualquer IP dela responde.
um IP, como 192.168.1.10Só aquela interface. Útil numa máquina com mais de uma rede (por exemplo, atender só a rede de gerência).

Rodando o jar:

OMNIDUDE_BIND=0.0.0.0 java -jar target/omnidude-0.1.0-SNAPSHOT.jar

Com o serviço systemd: edite o arquivo de ambiente e reinicie.

sudo nano /etc/omnidude/omnidude.env      # descomente/ajuste: OMNIDUDE_BIND=0.0.0.0
sudo systemctl restart omnidude
journalctl -u omnidude -n 20              # confira o aviso de escuta (veja abaixo)

Depois, abra http://IP-DA-MAQUINA:8080 em outro computador. Para descobrir o IP: hostname -I.

  1. Libere a porta no firewall da máquina, de preferência só para a sua rede: 
    # Ubuntu/Debian (ufw)
sudo ufw allow from 192.168.1.0/24 to any port 8080 proto tcp

# RHEL/Fedora (firewalld)
sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" port port="8080" protocol="tcp" accept'
sudo firewall-cmd --reload
  2. Entre normalmente com o usuário e a senha. O login funciona com o cookie padrão.
  3. Troque a senha provisória logo no primeiro acesso, sabendo que ela trafegou sem criptografia (veja abaixo).

O que muda e o que observar

  • Aviso no log. Ao escutar fora de 127.0.0.1 sem TLS nem proxy, o OmniDude registra: “escuta em 0.0.0.0 sem TLS: senhas e a sessão trafegam em texto puro”. É esperado nesta opção; serve para você não esquecer.
  • Texto puro. A senha, o cookie de sessão e todos os dados passam sem criptografia. Quem estiver no mesmo segmento de rede pode capturá-los. Numa rede interna confiável costuma ser aceitável; em Wi-Fi compartilhado ou fora dela, não.
  • Não ligue OMNIDUDE_COOKIE_SECURE=true com acesso por HTTP: o navegador descarta o cookie e o login “não pega”. Essa variável é só para HTTPS.
  • Porta abaixo de 1024. A unidade systemd não concede CAP_NET_BIND_SERVICE, então o serviço não consegue usar as portas 80 ou 443. Use uma porta alta (OMNIDUDE_PORT=8080) ou a opção C.
  • Mapa público. O link gerado usa o endereço pelo qual você abriu o OmniDude. Aberto pelo IP da máquina, ele sai com esse IP e só funciona para quem alcança esse IP. A tela de publicação avisa quando o endereço é local.
  • Descoberta, SNMP e checagens não dependem desse ajuste: elas são conexões de saída do servidor.
  • As proteções de login, CSRF e perfis continuam valendo. O que muda é só o tráfego estar sem criptografia.

Opção B: TLS no próprio OmniDude

O OmniDude pode servir HTTPS sozinho, com um certificado em formato PKCS12 (.p12). Não precisa de proxy.

  1. Gere ou obtenha o certificado. Para um teste, um autoassinado (o navegador vai avisar que não é confiável): 
    keytool -genkeypair -alias omnidude -keyalg RSA -keysize 2048 -storetype PKCS12 \
        -keystore omnidude.p12 -storepass TROQUE-ESTA-SENHA -dname "CN=omnidude" -validity 365
    Com um certificado de verdade (por exemplo, do Let's Encrypt), converta-o: 
    openssl pkcs12 -export -in fullchain.pem -inkey privkey.pem -name omnidude \
        -out omnidude.p12 -passout pass:TROQUE-ESTA-SENHA
  2. Guarde o arquivo onde o serviço o leia e proteja-o. No systemd: 
    sudo install -m 0640 -o root -g omnidude omnidude.p12 /etc/omnidude/omnidude.p12
  3. Configure em /etc/omnidude/omnidude.env (modo 600) e reinicie: 
    OMNIDUDE_BIND=0.0.0.0
OMNIDUDE_PORT=8443
OMNIDUDE_COOKIE_SECURE=true
SERVER_SSL_ENABLED=true
SERVER_SSL_KEY_STORE=/etc/omnidude/omnidude.p12
SERVER_SSL_KEY_STORE_PASSWORD=TROQUE-ESTA-SENHA
SERVER_SSL_KEY_STORE_TYPE=PKCS12
  4. Acesse https://IP-DA-MAQUINA:8443 e libere a porta no firewall, como na opção A.

Rodando o jar, as mesmas variáveis servem (ou use as propriedades --server.ssl.enabled=true, --server.ssl.key-store=…, --server.ssl.key-store-password=…).

  • Com TLS ligado, o cookie de sessão sai com Secure e o servidor envia Strict-Transport-Security (HSTS). O aviso de “sem TLS” some.
  • Não use OMNIDUDE_FORWARD_HEADERS aqui: ele é só para proxy reverso.
  • Um certificado renovado só vale depois de sudo systemctl restart omnidude.
  • O certificado precisa ter o nome (ou IP) pelo qual você acessa; com um autoassinado, cada navegador pede para aceitar a exceção.

Esta opção foi exercitada com um certificado autoassinado (acesso pelo IP da máquina, cookie Secure e HSTS conferidos). A renovação automática de certificados (por exemplo, com certbot) fica por sua conta; com um proxy (opção C) ela costuma ser mais simples.

Opção C: proxy reverso com HTTPS (recomendada)

Mantenha o OmniDude em 127.0.0.1 e ponha um proxy reverso com TLS (nginx, Caddy, Apache) na mesma máquina. O proxy cuida do certificado e da renovação, pode servir outros sistemas na porta 443 e aplicar limites de requisição. Em /etc/omnidude/omnidude.env:

OMNIDUDE_FORWARD_HEADERS=native
OMNIDUDE_COOKIE_SECURE=true

Exemplo para o nginx. O proxy deve substituir os cabeçalhos X-Forwarded-* e desligar o buffering do canal de eventos em tempo real (/api/stream):

server {
    listen 443 ssl;
    server_name omnidude.exemplo.com;
    # ssl_certificate / ssl_certificate_key ...

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    location /api/stream {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;
        proxy_read_timeout 1h;
    }
}
  • Se o proxy estiver em outra máquina, o OmniDude precisa escutar numa interface que ele alcance (opção A, OMNIDUDE_BIND=IP, com firewall só para o proxy) e OMNIDUDE_TRUSTED_PROXIES com o IP dele (expressão regular, por exemplo 10\.0\.0\.5).
  • Não use OMNIDUDE_FORWARD_HEADERS=framework: ele confia em qualquer origem e permite falsificar o IP do cliente.

Veja o capítulo de segurança para o restante das recomendações.

Contêineres

Ainda não há Dockerfile oficial: ele está no roteiro. Enquanto isso, o jar roda em qualquer imagem com Java 21; lembre-se de montar um volume em OMNIDUDE_DATA_DIR e de que o ICMP precisa do ping e da capacidade NET_RAW dentro do contêiner.
